## Why this matters

Two independent one-version-too-low pins are each leaving a set of
already-fixed-upstream CVEs open in this repo, confirmed against the live
lockfile:

1. **`undici` override floor is one patch below the fix.**
   `pnpm-workspace.yaml`'s `overrides` block pins `undici: ">=7.28.0"`.
   `pnpm why undici` resolves this to exactly `undici@7.28.0` (pulled in
   transitively via `astro-icon > @iconify/tools > cheerio > undici`).
   `pnpm audit` flags this exact version for 4 advisories (2 high — a
   ReDoS in retry-interceptor response handling and a cross-user
   cache-control disclosure; 2 moderate — CRLF injection via blob `type`
   and cookie-attribute injection) all fixed in `undici@>=7.29.0` — one
   patch above the floor this repo currently enforces. The override exists
   specifically to pin a version believed safe; the floor is simply one
   version too low to actually achieve that.
2. **`@astrojs/node` lags one patch behind Astro core, duplicating a
   vulnerable `js-yaml`.** `package.json` pins the `@astrojs/node`
   devDependency to `11.0.2`. `pnpm why js-yaml` shows **two** resolved
   versions in the tree: `js-yaml@4.2.0` (vulnerable — high severity,
   GHSA quadratic-CPU YAML merge-key parsing, fixed in `>=4.3.0`) via
   `@astrojs/node@11.0.2 > @astrojs/internal-helpers@0.10.1`, and the
   already-patched `js-yaml@4.3.1` via every other path in the tree
   (`astro@7.1.6`'s own `@astrojs/internal-helpers@0.10.2`). `pnpm
   outdated` confirms `@astrojs/node@11.0.3` is already released and
   available, and it depends on the same `@astrojs/internal-helpers@0.10.2`
   (and thus the patched `js-yaml`) that the rest of the tree already uses
   — bumping this one devDependency removes the duplicate vulnerable copy
   entirely rather than just adding an override on top of it.

Both are one-line, low-risk patch/floor bumps.

## Steps

### Step 1: Bump the `undici` override floor

In `pnpm-workspace.yaml`, change:
```yaml
  undici: ">=7.28.0"
```
to:
```yaml
  undici: ">=7.29.0"
```

**Verify**: `grep -n "undici" pnpm-workspace.yaml` → shows `>=7.29.0`.

### Step 2: Bump `@astrojs/node`

In `package.json`, change:
```json
    "@astrojs/node": "11.0.2",
```
to:
```json
    "@astrojs/node": "11.0.3",
```
(Match the existing pin style — this repo pins `@astrojs/node` to an exact
version with no `^`/`~` range prefix, unlike most other deps in this
`package.json`; keep that same exact-pin style, don't add a range
operator.)

**Verify**: `grep -n '"@astrojs/node"' package.json` → shows `11.0.3`.

### Step 3: Reinstall and confirm the lockfile picks up patched versions

```
pnpm install
```

**Verify**:
- `pnpm why undici` → resolves to `undici@7.29.0` or higher, only one
  version present.
- `pnpm why js-yaml` → resolves to a single version (`4.3.1` or higher),
  no second `4.2.x` copy remaining.
- `pnpm audit` → the 4 previously-listed undici advisories (GHSA IDs for
  the ReDoS/cache-disclosure/CRLF-injection/cookie-injection issues) and
  the js-yaml quadratic-CPU advisory no longer appear in the output.

### Step 4: Confirm the build and local preview path still work

`@astrojs/node` is used for this repo's `PREVIEW=true` local-preview
adapter path (`astro.config.mjs`) — a patch bump should be
backwards-compatible, but confirm rather than assume:

```
pnpm build
pnpm preview-build && pnpm preview-start
```

**Verify**: both exit 0 / start without error. If `preview-start` starts a
long-running server, it's sufficient to confirm it boots without an
immediate crash/error in its startup log, then stop it — no need to leave
it running.

## Deviation from plan (drift found at execution time)

package.json`) fired: `package.json` had changed since the plan was

instructions showed `@astrojs/node` was already at `11.1.0` (past the
`11.0.3` target) and `pnpm why js-yaml` already resolved to a single patched

`pnpm audit` confirms both advisory families (undici and js-yaml) are gone
and no new advisories were introduced.
