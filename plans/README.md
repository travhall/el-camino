## Initial-page-load investigation (2026-09-05, commit `ad2999d`) — Plans 146-151

Motivating report: *"animations run fine if the page has already loaded or is
cached, but the initial page load is always choppy or takes a long time to
render"*, with Lighthouse scores already at their best-ever levels.

**Why Lighthouse missed it.** Unthrottled, production's homepage LCP is
**296 ms** — genuinely good. The defect only appears under load, and its core
symptom (entrance animations playing against content that has not arrived yet)
is a *scheduling* problem that no Lighthouse audit measures. Two Chrome
DevTools traces of live production, same page, were the instrument:

| | unthrottled | Slow 4G + 4x CPU |
|---|---|---|
| LCP | 296 ms | 1295 ms |
| TTFB | 147 ms | 425 ms |
| LCP resource load delay | 3 ms | 270 ms |
| LCP resource load duration | 42 ms | 570 ms |
| CLS | 0.04 | 0.07 |
| requests | — | 54 (~40 JS chunks) |

**Root causes found** (each became a plan):

1. **Every transformed image is uncacheable in the browser** (Plan 146) —
   `cache-control: public,max-age=0,must-revalidate` on every
   `/.netlify/images` response, on **both** production and staging. The
   `netlify.toml` rule written to fix this (`for = "/.netlify/images/*"`) has
   never fired: the endpoint is addressed by query string, not path, *and*
   `netlify.toml` headers do not reach that internal endpoint at all — proven
   by the image response carrying none of the `for = "/*"` security headers and
   an HSTS value that is Netlify's default rather than this repo's configured
   one. Per Netlify docs the transform inherits `Cache-Control` from the
   **source**, and both sources are unfixable from here: wordpress.com sends no
   `Cache-Control` and an `expires` date already in the past; Square's S3 sends
   no cache headers at all.
2. **Placeholder removal is gated behind the whole JS module graph** (Plan
   147) — `imageShimmer.ts` is a deferred module that only acts on
   `astro:page-load`. In the trace it was **request 51 of 54**. Images decode
   at 1265 ms; their skeletons stay up until the module waterfall settles.
3. **Card entrance animations are keyed to CSS parse time** (Plan 148) — they
   run ~830→1780 ms while the LCP image lands at 1265 ms, so cards animate in
   empty and images pop in afterwards. On a warm cache the two coincide, which
   is exactly why the symptom only ever appears on the load that matters.
4. **Font preloads outrank the LCP image** (Plan 149) — 119 KB of WOFF2
   preloaded twice (in-document `<link>` *and* an HTTP `Link:` header in
   `netlify.toml`, the latter starting before HTML parsing), with
   `fetchpriority="high"` on Alumni. LCP resource load delay: 270 ms, 21% of
   the metric. Both `preconnect` hints also flagged unused by the
   `NetworkDependencyTree` insight.
5. **`sizes` mismatch wastes the LCP preload** (Plan 150) — the preload says
   `(max-width: 640px)`, the `<img>` says `(max-width: 767px)`. Viewports
   641-767 px select different `srcset` candidates, so the image downloads
   twice. `767px` is correct (`md:grid-cols-6`; Tailwind v4 `md` = 768px).
6. **Hero AVIF is heavy** (Plan 151) — 143,968 bytes at `w=1024&q=75` from a
   165,600-byte source JPEG: ~13% saved. 44% of the throttled LCP.

**Explicitly ruled out during this investigation** (do not re-audit):

- **Nav viewport-prefetch.** Plan 128 landed; all `prefetchStrategy` values in
  `Nav.astro` are now `"hover"`, verified by grep. The `/the-shop` and `/news`
  full-document fetches visible in the trace are the headless browser's cursor
  resting at (0,0) over the nav and triggering hover-prefetch — a test artifact,

  146/148 rather than being a separate finding.
- **WordPress image/content sourcing generally.** The maintainer has stated the
  limitations of the headless-WordPress image pipeline are known and accepted.
  146 and 151 work *within* that constraint rather than proposing to replace it.

## Square deep-dive findings (2026-07-01, commit `56226fb`) — all four planned (021-024)

A focused pass over the cart/checkout/Square integration surfaced the
findings below; the maintainer selected all four for planning.

Correction made during plan-writing: the initial summary presented to the
maintainer described `src/lib/square/apiUtils.ts`'s `CircuitBreaker` as
equivalent to `src/lib/square/apiRetry.ts`'s `ApiRetryClient`. Reading
`apiUtils.ts`'s `execute()` closely shows it calls the wrapped function
**once** — on failure it only increments a counter toward eventually
failing fast, it never retries the call itself. `apiRetryClient` actually
retries with backoff/jitter/timeout and has its own internal circuit
breaker — it's the strictly more capable of the two. This changed which
utility Plans 021 and 024 standardize on (`apiRetryClient`, not
`defaultCircuitBreaker`) and reframed 024 from "delete dead code" to
"migrate the checkout-critical call sites that currently only get
fail-fast protection onto the utility that actually retries, then remove
the now-fully-unused weaker one."

- **Checkout-critical Square calls have no retry protection at all**:
  `squareClient.checkout.paymentLinks.create()` in
  `src/pages/api/create-checkout.ts:390` and `squareClient.orders.calculate()`
  in `src/pages/api/calculate-cart.ts:76` call the SDK directly with no
  wrapper of any kind. A transient Square 5xx/network blip at the exact
  moment a customer pays fails hard with a generic 500, even though
  `apiRetryClient` (real retry+backoff, already proven in
  `categoryUtils.ts`/`Nav.astro`) is one import away. → Plan 021.
- **The checkout-critical inventory/catalog path only has fail-fast
  protection, not retry**: `src/lib/square/client.ts` (`fetchProducts`,
  `fetchProduct`) and `src/lib/square/inventoryCore.ts:58` wrap their Square
  calls in `defaultCircuitBreaker.execute()`, which — per the correction
  above — never retries a failed call, only opens a circuit after repeated
  failures. Migrating these three call sites onto `apiRetryClient` gives
  them actual retry behavior; the now-unused `CircuitBreaker` class in
  `apiUtils.ts` (no remaining callers after migration) can then be removed,
  along with `apiRetry.ts`'s status as a barely-used utility despite
  carrying an enforced per-file coverage threshold in `vitest.config.ts`.
  → Plan 024.
- **`calculate-cart.ts` trusts client-supplied sale prices for the pre-checkout
  total preview**: `src/pages/api/calculate-cart.ts:32` uses
  `item.saleInfo?.salePrice` (attacker-/staleness-controlled via
  localStorage) when building the line items sent to Square's
  `orders.calculate`, unlike `create-checkout.ts:263`, which re-derives
  authoritative pricing via `getAuthoritativePricing()` before charging. No
  money is at risk (checkout re-derives correctly), but the *displayed*
  preview total on the cart page can diverge from what the customer is
  actually charged, which reads as a bug to the customer. Fix: call
  `getAuthoritativePricing()` in `calculate-cart.ts` the same way
  `create-checkout.ts` does. → Plan 022.
- **Free-shipping threshold and flat rate are hand-duplicated in three
  places**: authoritative values live in `src/lib/config/shipping.ts:35-49`
  (`rate: 5.99`, `freeThreshold: 75.0`); `src/components/FulfillmentSelector.astro:11-12`
  redeclares them server-side (`FREE_SHIPPING_THRESHOLD = 7500` cents,
  `FLAT_RATE_SHIPPING = 599` cents) for the tab label; the same file's client
  `<script>` (lines 462-463) redeclares them a third time in dollars for the
  progress-bar widget. A future rate change in `shipping.ts` silently
  desyncs the two display copies. → Plan 023.

Not planned (informational only, low confidence/low severity):
- `create-checkout.ts:601` (cart.astro) generates a fresh `checkoutKey`
  (idempotency key) on every click of "Continue to Payment" rather than
  reusing one across retries of the *same* attempt — if a request succeeds on
  Square's side but the response is lost before the client sees it, a
  follow-up click could create a second payment link/order. Low likelihood,
  and not a double-charge risk (the customer must complete a second payment
  to actually pay twice) — flagged for awareness, not worth a dedicated plan.
- `e2e/cart-flow.spec.ts`'s "should navigate to cart page and display items"
  test asserts button text `"Proceed to Checkout"`, but the live button says
